* **撰寫日期**：2026-11-22

## 一、 專案主題與製作動機

### 1. 為什麼選擇 Unity 2D 入門教學？
對於從未接觸過遊戲開發的大學生與程式初學者而言，Unity 是一套功能強大但同時極具挑戰性的引擎。初學者在第一次打開 Unity 編輯器時，面對密密麻麻的面板、數以百計的英文選單、複雜的 C# 腳本生命週期與物理碰撞公式，往往會產生巨大的挫折感而中途放棄。

本專案的動機在於：**為零基礎的初學者量身打造一套「以心智模型為核心」的 Unity 2D 極簡入門路徑**。我們跳過複雜的數學微積分與高階程式語法，聚焦在建立遊戲開發最關鍵的幾大基石——了解場景（Scene）與遊戲物件（GameObject）的容器關係、組件（Component）的功能組合、圖片渲染（Sprite Renderer）與圖層遮擋、地圖繪製（Tilemap）、腳本作為自訂組件（MonoBehaviour）、剛體物理（Rigidbody 2D）以及在工具列（Toolbar）進行 Play Mode 即時測試。

### 2. 「雪地狗狗場景」情境貫穿
為了讓抽象的架構具象化，我們在簡報中設計了「製作一個簡單的雪地狗狗場景」情境：從擺放狗狗與雪松樹（GameObject）、掛載圖片（Sprite Renderer）並用 Flip 轉身、解決狗狗與草叢的前後遮擋（Order in Layer）、像畫畫一樣刷出雪地地貌（Tilemap）、賦予腳本邏輯、加入重力下墜（Rigidbody 2D），最後在 Play Mode 中驗收。透過單一連續的場景範例，幫助初學者在腦海中串聯完整的製作流程。

## 二、 LLM Wiki 建立過程

本專案最核心的原則是**高透明度與嚴格溯源（Strict Grounding）**。HTML 簡報的所有內容、小測驗與說明，必須 100% 來自本地端建立的 Wiki，嚴格杜絕模型憑空外插未經驗證的技術。

### 1. 官方來源核定與收斂
在需求訪談初期，曾討論過是否匯入高達 14 篇涵蓋進階 API 的文件。然而，過多的來源會大幅增加知識管理與除錯複雜度。經評估後，我們果斷收斂並鎖定 **6 篇最基礎、權威的 Unity 6.0（6000.0 LTS）官方手冊**作為核心基石：
1. `Game objects`（基本概念與容器論）
2. `Sprite Renderer component reference`（2D 渲染與圖層排序）
3. `Tilemaps`（地圖繪製與調色盤流程）
4. `Creating scripts`（C# 腳本結構與自訂組件）
5. `Rigidbody 2D`（剛體、四大物理特性與模擬控制）
6. `The Toolbar`（頂部工具列與 Play Mode 測試）

### 2. 原始資料下載與降噪（`raw/`）
現代官方網頁往往包含數百 KB 的導覽抽屜、SVG 圖示、腳本 Bundle 與側邊欄目錄。在資料擷取時，我們透過 Python 腳本精準提取 `<article>` 正文區塊，將原始約 420 KB 的 HTML 網頁徹底清洗，轉化為約 2.5 KB ~ 6.6 KB 乾淨、結構化的 Markdown 文字檔存入 `raw/`，完整保留官方段落標題、內文與屬性表格。

### 3. 知識提煉與精準溯源（`wiki/`）
根據 `raw/` 原始檔案，我們以繁體中文重新編排為易讀的知識庫，並嚴格保留英文專有名詞。每個知識點均附帶四項標準溯源標籤：
* `【官方來源】`、`【原始網址】`、`【段落章節】`、`【適用版本：Unity 6.0】`
並在最後建立 `wiki/INDEX.md` 作為全專案的總索引與進度看板。

## 三、 Graph / Loop 工作流程設計

專案採用狀態機（State Machine）架構，定義了明確的推進節點、檢驗條件與退回修正路由：

```
[Node 0: Init Spec] ──(Pass)──> [Node 1: Batch Ingest (raw/)]
                                       │
                                       ▼
                                 [Node 2: Wiki Distill (wiki/)]
                                       │
                                       ▼
                                 [Node 3: Batch Verification]
                                  ├─ Pass ──> (完成 3 批後推進 Node 4)
                                  └─ Fail ──> [Node 2 修正] (Loop, max 3 次)
                                       │
                                       ▼
                                 [Node 4: Outline & Gap Report]
                                       │
                                       ▼
                                 【HITL 審查點：確認簡報大綱】
                                       │
                                       ▼
                                 [Node 5: Presentation Generation]
                                       │
                                       ▼
                                 [Node 6: Presentation Verification]
                                  ├─ Pass ──> [Node 7: Reflection & Delivery]
                                  └─ Fail ──> [Node 5 修正] (Loop, max 3 次)
                                       │
                                       ▼
                                 【HITL 審查點：最終驗收】
```

### 各節點職責與失敗退回規則
* **Node 0（規格定義）**：產出 `AGENTS.md`，明訂原則與終止條件。
* **Node 1（資料擷取）**：從官方 URL 下載原始資料並降噪。若擷取失敗或內容不全，退回 Node 1 重新擷取；若官方網址持續失效，立即中斷請求人工協助。
* **Node 2（知識提煉）**：整理為繁中 Markdown Wiki。若出現翻譯錯誤、引用格式缺失或模型幻覺，退回 Node 2 重新整理。
* **Node 3（批次檢驗）**：執行 C1（真實性）、C2（語言與名詞）、C3（溯源標籤）、C4（零幻覺）檢查，設定最多自動修正 3 輪（Retry $\le$ 3）。
* **Node 4（大綱與缺口審查）**：規劃簡報大綱並逐項檢視知識缺口，經人工確認（HITL Checkpoint）後方可進入生成。
* **Node 5（HTML 簡報生成）**：依大綱生成單一獨立 HTML 檔案（內嵌 CSS/JS/SVG）。
* **Node 6（簡報檢驗）**：檢查離線可用性、10 頁完整度、互動功能與免責聲明。若程式有誤退回 Node 5 修正（最多 3 輪）。
* **Node 7（反思與交付）**：彙整全流程真實日誌，產出反思與繳交資料，進行最終人工驗收。

## 五、 最容易出錯或最需要注意的節點分析（真實經驗）

在本次端對端的執行過程中，我們觀察到三個最關鍵且最容易產生隱形錯誤的環節：

### 1. Node 1 原始資料擷取時的 HTML 雜訊清洗
現代網頁架構高度動態化，若直接儲存網頁原始代碼，會有超過 98% 的內容是與教學無關的選單抽屜、按鈕與 JavaScript 代碼。若沒有嚴格限定只擷取 `<article>` 正文區塊並轉換為 Markdown 表格，這些雜訊將直接污染 `raw/` 目錄，導致後續 Wiki 提煉時模型容易迷航或抓錯欄位。

### 2. Node 2 與 Node 4 的 Strict Grounding（防範技術幻覺）
這是在生成式 AI 開發中最具挑戰性的一點。模型在預訓練階段已掌握大量 Unity API（如 `Input.GetAxis`、`Collider2D`、`SceneManager`）。在規劃大綱時，稍不留意就容易「順手」把這些外部知識寫進簡報中。我們透過建立專屬的「知識缺口報告（`knowledge_gap_report.md`）」，嚴格強制執行「不在 6 篇文件裡的技術，一律簡化教學或完全刪除」，成功守住了 100% 溯源的底線。

### 3. Node 5 前端鍵盤事件的衝突防範
在單頁 HTML 簡報中，如果同時存在「全域切換投影片」與「局部控制角色移動」兩種鍵盤監聽，非常容易發生「按一次方向鍵，角色走一步同時投影片也跳了一頁」的嚴重衝突。這提醒我們在前端設計時，必須嚴謹規劃按鍵職責分離（將移動收斂給 WASD，左右鍵專屬切頁）。

## 六、 如果重新設計工作流程的優化建議

若未來重新執行類似專案，我會提出以下兩項流程提前（Shift-Left）優化：

1. **將「前端互動操作規範與按鍵分工」提前至 Node 4（大綱規劃階段）明確定義**：
   本次專案在初版大綱中僅粗略規劃「狗狗移動支援鍵盤操作」，直到階段 3 實作時才發現 WASD 與方向鍵的衝突問題，並在階段 4 進行程式碼與文件的修訂。若能在 Node 4 大綱階段就提早把按鍵分工（WASD 專屬控狗、方向鍵專屬切頁）規格化，便能省去後續一次程式碼重構的時間。
2. **提前建立原始資料擷取模板（Ingestion Pipeline Template）**：
   在第一批抓取前，先固化好去除 SVG、抽離 Table、過濾 Header/Footer 的標準轉換函數，讓 Node 1 的自動化程度更高、更穩健。

## 七、 本次工作流程（Workflow）的修改與調整紀錄

在專案執行期間，我們根據實際情況對工作流程進行了真實且透明的調整，嚴格記錄於 `logs/execution_log.md` 中：

1. **改採「逐階段人工確認（HITL Checkpoints）」**：
   原規格允許模型在通過檢查後自動推進下一個批次。但為了確保資料與程式碼絕對受控，我們在實際執行時加入了嚴格的「每完成一批資料或一個階段，即刻停止並向使用者回報確認」規則，全專案共落實了 5 個關鍵檢查點。
2. **P8 鍵盤操作規則的人工調整**：
   在階段 3 生成簡報後，經人工檢驗發現第 8 頁方向鍵鎖定導致切頁不便，使用者提出需求進行優化：將狗狗控制限定於 WASD、方向鍵全面釋放給全域切頁。**此處為「人工驗收後的需求規格微調」，並非「AI 自動檢查失敗觸發 Loop」**，我們在日誌與反思中如實分開記錄。
3. **Loop 重試次數真實性**：
   在第一批至第三批的 Ingest 檢驗（Node 3）中，由於規範清晰且限縮得當，檢查結果均為一次通過（Retry Count = 0）。我們如實記錄 0 次重試，絕不為了形式好看而事後虛構錯誤或自動修正紀錄。

## 八、 本次學習心得

這次作業是一次對「如何正確駕馭生成式 AI」的深刻洗禮。

在過去的學習經驗中，我們往往習慣將 AI 當作「問答機器」——丟出一個問題，直接索取最終答案或完整程式碼。這種用法看似快速，但在開發稍微複雜或講求嚴謹度的專案時，往往伴隨著難以除錯的幻覺代碼、不知從何而來的技術拼湊，以及缺乏整體架構的一致性。

而在本次「Unity 2D LLM Wiki 與簡報系統」的開發中，我們採用了截然不同的軟體工程思維：
1. **知識庫先行（Grounding First）**：先建立真實、透明、可追溯的資料底座（Wiki），讓 AI 的回答有「法」可依。
2. **流程約束與狀態機（Graph / Loop）**：將大任務拆解成細部節點，定義明確的通過與退回標準，讓 AI 在既定軌道內運作。
3. **人機協同（Human-in-the-Loop）**：在需求定義、大綱規劃與關鍵節點保留人類審查的主導權，AI 負責高效率的執行與提煉，人類負責方向把關與決策。

這讓我體會到：**生成式 AI 最強大的力量並不在於天馬行空的發揮，而在於與嚴謹的軟體流程設計結合**。透過架構、邊界與日誌記錄，我們才能真正創造出高可用、零幻覺、且值得信賴的專業數位成果。
